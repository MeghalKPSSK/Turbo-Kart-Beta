Findings:

1. **The two sprint routes are the heavy ones.** 866 draw calls each; Crosstown Sprint
   dropped to 26 frames per second. Sixteen traffic vehicles at 17 to 20 thousand triangles
   each are a large part of that.
2. **Memory grows across a session.** The JavaScript heap rose from 65 MB to 133 MB over
   16 races and did not come back down. Loaded route and vehicle models are cached for the
   life of the page with no limit.
3. **Not tested:** the eight vehicles individually on every route (the physics suites cover
   one car and one bike per test), a physical gamepad, a real phone, and any browser other
   than the app's built-in one.

## 3. Asset delivery (Verified) and resolution plan (Proposed)

- `public/` is the source of truth; `docs/` is the built copy that GitHub Pages serves.
- `docs/` differs from `public/` in exactly four files: the four bike models. Nothing is
  missing and nothing is stale beyond that.
- `main` and the live site do not have the street cars, the modelled traffic, the bikes or

Resolution: commit the bike work, run `npm run build` to refresh `docs/`, then add a
check to `npm test` that fails when any file under `public/` differs from its copy in

## 4. Save-data schema (Verified from `src/state/`)

Two `localStorage` keys.

`turbo-road-league-profile-v3`:

| Field | Type | Meaning |
|---|---|---|
| `version` | number | 3 |
| `credits` | number | The only currency |
| `xp` | number | Driver experience; level is derived |
| `races`, `wins`, `bestFinish`, `bestTime`, `bestScore`, `totalPoints`, `takedowns` | numbers | Records |
| `owned` | string[] | Vehicle ids |
| `garage` | `{ vehicleId: { speed, accel, handling, nitro, armor } }` | Upgrade levels 0 to 5 |
| `stars` | `{ eventId: 0..3 }` | Career results |
| `bosses` | string[] | Tier ids whose boss is beaten |
| `cups` | `{ cupId: bestPlace }` | Cup results |
| `activeCup` | `null` or `{ id, round, points }` | Cup in progress |

`keysVersion`.

Existing migrations: profile v1 to v2 to v3 (road coins became credits; old story progress
dropped) and one key-binding migration. There is no revision counter, timestamp or
checksum, and a corrupted profile silently becomes a fresh one.

## 5. Race lifecycle and module map (Verified)

```
App.jsx (319 lines)
  screen state, mode (career | cup | quick | garage), selected vehicle / route / event
  buildSetup()  ->  { track, vehicle, paint, upgrades, rules, labels }
  useEffect     ->  new RoadRaceGame(host, setup, callbacks)   one instance per race
  onFinish      ->  applyRaceResult(profile, result, setup)    in src/state/profile.js
  useRaceInput  ->  keyboard, gamepad, touch  ->  game.setInput / setAnalog

RoadRaceGame.js (1,204 lines)
  init: load route, physics engine, vehicles, traffic  ->  TrackModel, PhysicsWorld
        cityLook (city routes only), TrafficSystem, racers (Vehicle + AIDriver + visuals)
  loop: fixed 120 Hz  ->  controllers (60 Hz), traffic.step, physics.step
        per frame     ->  collisions, recovery, pickups, race state, event rules, HUD
  finish -> result object -> App

Pure, browser-free (already used by the headless tests):
  physics/  ai/  data/career.js  state/profile.js  systems/collisions.js  raceRules.js
Browser-only:
  RoadRaceGame.js  cityLook.js  traffic.js  effects/  audio/  screens/  components/
```

Observations for the roadmap's architecture section:

- Career and save logic are **already** outside React, in `career.js` and `profile.js`,
  and are unit-tested. The proposed "CareerManager" and "SaveManager" largely exist.
- `RoadRaceGame.js` is large but its 60 fps cost is rendering, not its own code. I see no
  evidence yet that splitting it would help performance. It would help readability.
- The cleanest first extraction is the career event rules (elimination, time limit,
  pursuit), which are about 120 lines inside `RoadRaceGame.js`.

## 6. Save migration strategy (Proposed)

1. Wrap the profile in an envelope: `{ schema: 4, revision, updatedAt, syncedAt, conflict,
   data }`. `revision` increments on every write.
2. Move the profile to IndexedDB, keep settings in `localStorage`. On first run copy the
   v3 profile across and leave the old key in place as a backup for one release.
3. Keep the last three revisions, so a corrupted save restores the previous one instead of
   resetting the player.
4. Add tests for: v1, v2 and v3 saves loading; a corrupted save falling back; a newer
   schema than the code understands being left untouched.

Acceptance: an existing player's credits, garage, stars and cups are identical after the
upgrade, and the game still starts with storage blocked.

## 7. Online services proposal (Proposed, nothing built)

Offline play never calls the server. The client syncs when signed in and online.

| Endpoint | Purpose |
|---|---|
| `POST /auth/register`, `/auth/login`, `/auth/refresh`, `/auth/logout` | Account, access token plus refresh token |
| `GET /profile`, `PATCH /profile` | Display name, driver level, public statistics |
| `GET /save`, `PUT /save` | Cloud save. `PUT` carries the client revision; the server answers 409 with its copy when revisions diverge |
| `POST /results` | Submit a finished event with the inputs needed to check it |
| `GET /leaderboards/:routeId?mode=timeTrial` | Top times plus the player's own rank |
| `GET /events/current` | Weekly challenge definitions |
| `GET /achievements`, `POST /achievements/claim` | Server-checked claims |

Tables: `users`, `player_profiles` (own id, separate from `users`), `player_saves`
(revisioned blob), `player_wallet`, `player_vehicles`, `vehicle_upgrades`,
`race_results`, `leaderboard_entries`, `player_achievements`, `game_events`.

Server-checked, never last-write-wins: credits, vehicle ownership, competitive results and
achievement claims. A submitted lap time is rejected if it beats what the route length and
the vehicle's top speed allow.

Stack as the roadmap states: Node.js, Express, MySQL. No Redis until matchmaking needs it.
This needs hosting you pay for; GitHub Pages cannot run it.

## 8. What the reference pictures ask for, and what I can deliver

I read the 20 pictures as five targets:

| Target in the pictures | Where the game is now | What I can build |
|---|---|---|
| Night city with neon signs, billboards and wet reflective streets | Dusk city, lit windows, no signage, dry road | Signage and billboards with invented brand names, a night sky variant, wet-road reflections, more street light |
| Mountain and forest roads: textured rock, snow caps, dense autumn trees, mist, guardrails, road signs | Eight scenic circuits with flat generated colours and no scanned trees | Rebuild the scenic circuits with photographic rock, grass and snow textures, real skies, forests of the scanned trees, mist, guardrails and signs |
| Coastal highway with sea, cliffs and strong sunlight | Two coastal circuits in the old look | Same rebuild, with a water surface and a daylight sky |
| Detailed cars: panel lines, vents, wings, diffusers, lamp clusters, tread | Smooth lofted bodies with glass, lamps and alloys; no panel lines or aero parts | A detail pass: shut lines, vents, splitters, wings, diffusers, lamp clusters, tyre tread, cabin silhouettes |
| Sport bike with sculpted fairing and a natural rider | Welded rider with creases; fairing is still a rounded blob | Panel-built fairing, tank and tail; gloves and boots with shape |

Three limits I want to be plain about:

1. **I will not copy the cars in the pictures.** Several are real production cars and the
   screenshots are from existing commercial games. I will design original vehicles and
   scenery in that spirit, not reproduce a specific car, badge, track or game.
2. **Those pictures are console games and offline renders.** A browser on a laptop cannot
   match them. A realistic target is "good-looking modern web game": the gap will narrow a
   lot, not close.
3. **Script-built models have a ceiling.** For cars at the level of the wireframe
   pictures, the practical route is licensed or purchased models that you choose, which I
   then fit into the game.
